# Connexion contract-assisted evaluation protocol v1

## Historical benchmark semantics (unchanged)

The published baseline, external, and combined reports are generated by
`backend/app/evaluation/runner.py`. For every case, `run_single_case_analysis`
normalizes source with `normalize_source_tree(loaded_source)` and does not pass
the OpenAPI specification into source normalization. `SPEC_ONLY` evaluates
specification findings. `SOURCE_ONLY` evaluates findings from that contract-free
source tree. `CORRELATED` correlates those findings with the specification, but
the source tree itself still contains only routes extractable from source
decorators. Connexion routes declared only by OpenAPI are therefore absent from
all three historical conditions. This protocol does not change that behavior,
the labels, or any published artifacts.

Production scans are a different path: `backend/app/services/analysis_worker.py`
passes the normalized specification to `normalize_source_tree`, allowing the
static Connexion extractor to map dotted operation IDs to source handlers.

## Research question and scope

Does static registration recognition avoid unrelated `.add_api()` receivers,
and, when a registration is provable, map dotted contract operation IDs to the
declared source handler with correct source-file and line provenance? This is a
small implementation-conformance evaluation, not a vulnerability-detection
benchmark and not evidence of generalization to arbitrary Connexion applications.

The independent, hand-authored structural expectations live in
`evaluation/connexion_protocol/v1/cases.json`. They describe literal fixture
facts: app construction, registration receiver, operation ID, handler
declaration, and expected declaration line. They do not reuse or alter either
security ground-truth dataset. Cases cover direct registration, imported and
assignment aliases, an unrelated receiver, an ambiguous dynamic factory, and a
registered contract whose handler is absent.

## Evaluation rules and metrics

Only this protocol supplies an OpenAPI-like normalized contract to source
normalization. It uses `connexion-contract-assisted-v1` as its independent
version identifier. Registration is scored as TP/FP/FN/TN with precision and
recall. Mappings are exact tuples of method, path, handler, and source file,
scored with TP/FP/FN, precision, and recall. Evidence provenance passes only
when each expected mapping points to the expected source file and exact handler
declaration line. Failure categories are `false_registration`,
`missed_registration`, `false_mapping`, `missed_mapping`, and
`wrong_evidence_provenance`.

The protocol intentionally does not score authentication correctness or
vulnerability labels. Authentication helper calls remain indicators, not proof
of enforcement. Dynamic factories, reassignments to unknown values, and other
control-flow-dependent registration are conservatively unsupported.

Run it from `backend/` with an explicit temporary output directory:

```sh
uv run python -m app.evaluation.connexion_protocol_v1 --output-dir /tmp/connexion-v1-run
```

The JSON result includes the protocol version and fixture-manifest SHA-256.
Reproducibility requires two runs from the same code and fixtures to have
identical result bytes and hashes. Keep these outputs separate from
`evaluation/reports/`; they are not publication-ready security performance
results. To support broader claims, a future protocol version needs a larger,
independently reviewed mapping corpus and separately adjudicated security
labels. Do not retrofit those labels from the existing vulnerability datasets.
